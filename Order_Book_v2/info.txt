-------------------Terms-----------------
1. Good_Till_Cancel: Order remains active until it's fully filled or manually cancel at a specifc time (so price, order_id, maintatining how many are left is important in this case)
2. Fill_and_Kill: the order is checked immediately against the current listed at orderbook side which user asked for and any reamining are canceled so partail order can be there.
3. Fill_or_Kil: In this if the order is not filled fully at the time the whole order is cancel (easier as just to need check if at that price is the quanity is >= asked )
4. Good_for_day: The order will remain active for a day only (so time contrant is added a new order_book type )
5. Market: Means the price is not a issue by user they just want there order to be filled at the price avalible

--------------Logic-----------------
1. Since code is running a mutex + thread + condition_value which can't be copied we need to make sure that the other 3 constructor are deleted
    all 5 constructor are:
    1. Default [ Orderbook() ]
    2. copy constructor [ Orderbook& ] -> Creates a new object as a copy of an existing one
    3. copy assignment [ void operator=( const Orderbook& ) ] -> Overwrites an existing object with another's contents
    4. move constructor [ Orderbook&& ] -> Creates a new object by stealing from a temporary
    5. move assignment [ void operator=( const Orderbook&& ) ] -> Overwrites an existing object by stealing from a temporary
    6. destructure 
2. temporary here means an unnamed object created by complier to hold a valu just long enough to use it then it deleted it ex any variable which is not used or changed after 
3. Due to RAII (Resource Acquistion is initialization ) we don't need to explicity handle the release of resource as RAII gurantee that the Acquired resource 
    will be release when the lifetime of their controlling object ends, in reverse order of acquisition.
